# SleepLens v1：评估、版本管理与商业测算更新方案

日期：2026-11-27  
状态：实施计划，尚未作为本方案完成正式实测。

本方案将当前 v1 建立为第一份可复核的基线：先确定指标和统计口径，再进行实测；后续每次更新，都比较质量、成本和延迟的变化。以下数字是建议的初始验收标准，不是教师规定，也不是已有成绩，应在正式测试前确定。

## 当前基础与主要缺口

项目已有评分规则、离线测试和调用日志，可以在这些基础上补齐。主要缺口为：

- 缺少统一的业务目标、评价指标和验收阈值。
- 缺少将代码、prompt、knowledge、业务规范和数据绑定起来的完整 agent 版本记录。
- 缺少跨多轮任务的请求、成本和延迟汇总。
- 缺少带有对照数据、成本来源和情景假设的商业测算表。

当前可复用的评分文件为 `docs/REVIEW_RUBRIC.json`，实施时应将其版本名称与当前 v1 对齐。

## 1. 明确业务目标、评价指标和验收阈值

业务目标：帮助成年用户更快、更准确地理解已有睡眠记录，并验证品牌提供这一功能是否值得投入。

| 目标 | 评价指标 | 建议初始验收阈值 |
| --- | --- | --- |
| 准确完成用户问题 | 完整任务通过率：正确、答全、范围一致、有适用依据 | ≥90%，同时报告成功数/尝试数 |
| 正确读取和计算记录 | 日期、档案、分母、数值及缺失处理正确率 | 测试集中100%正确，允许规定的舍入误差 |
| 保持安全边界 | 编造记录、越权操作、泄密、无依据诊断或个体用药方案的次数 | 观察到的严重失败为0；出现则暂停进入试点 |
| 回答具有一致性 | 同一道题重复运行全部通过的题目比例 | ≥80%，同时保留每次结果 |
| 使用体验可接受 | 含模型请求的用户轮次耗时 | 暂定中位数≤15秒、P95≤30秒 |
| 比现有方式更有帮助 | 用户理解正确率、任务完成时间 | 正确率不低于对照流程，完成时间中位数减少≥20% |

各指标分别判断，不能用表达流畅的高分抵消错误数字或严重越界。小样本下“零严重失败”只说明本次未观察到，不代表零风险；延迟分位数也应附样本量。

继续使用现有评分规则，但明确区分三个方面：任务是否成功、事实与证据是否正确、表达是否清楚。正式测试前固定评分规则和验收阈值；后续调整须说明原因并记录版本。

## 2. 建立 agent 版本及评测记录

增加整体 `agent_version`，从 `agent-v1` 开始。Prompt、knowledge、业务规范各自保留版本；每次评测保存完整配置和文件哈希。

| 每版需要记录 | 内容 |
| --- | --- |
| 版本身份 | agent、prompt、knowledge、业务规范、代码及数据快照 |
| 运行条件 | 日期、请求模型、实际返回模型、服务端点、生成参数 |
| 评测条件 | 测试集版本、评分规则版本、重复次数、评分者 |
| 结果 | 任务通过率、重复一致性、严重失败、成本、延迟 |
| 改动依据 | 问题编号、原始证据、根因、主要修改、同题复测及回归结果 |

后续更新流程：

1. 登记发现的问题，保留原始输入、最终展示和运行轨迹。
2. 分析根因，区分指令、知识、检索、生成、工具、任务路由或服务故障。
3. 修改并发布新的 agent 版本，例如 `agent-v2`；记录主要改动及对应组件版本。
4. 在相同条件下复测原题，并运行固定题集回归。
5. 比较修复的题目与新增失败，检查成本和延迟变化。
6. 最终检查使用尚未用于调整的新题；题目一旦用于修复，后续作为已知回归题。

版本比较保留逐题结果，不只显示总分。汇总表示例如下，所有数据均待实测：

| 版本 | 完整通过/尝试 | 全部重复通过的题数 | 严重失败 | 修复/新增失败 | 每成功任务成本 | 延迟中位数/P95 |
| --- | --- | --- | --- | --- | --- | --- |
| agent-v1 | 待测 | 待测 | 待测 | 基线 | 待测 | 待测 |
| agent-v2 | 待测 | 待测 | 待测 | 对比v1 | 待测 | 待测 |

代码或数据不同的结果，不能仅凭相同的版本名称混在一起；若测试集或评分规则改变，也必须标注，不能直接声称可比。

## 3. 补齐请求、轮次和任务的运营统计

### 3.1 统一统计单位

- **模型请求**：一次实际 API 调用。
- **用户轮次**：用户发送一次问题，可能触发多次模型请求。
- **业务任务**：完成一个目标，可能包含多轮追问。

增加 `task_id`，将同一任务的各轮及请求关联起来。补记录每次请求的耗时、输入/输出用量、错误类型、修正调用，以及任务最终是否完成。

### 3.2 修复现有统计缺口

- 本地回答分支目前将耗时写为 `0`，应改为实际计时。零 API 费用与零耗时分别记录。
- 分享日志主要保留总 tokens，精确计费还需要输入/输出用量、实际模型和计费来源等元数据。延续不保存对话正文的设置。
- 区分模型调用尝试与实际发送的 API 请求，避免把发送前的额度拒绝记为已发送请求。
- 保留失败、超时和额外调用的记录；无法取得用量时标记未知，不推断免费。

### 3.3 成本及延迟汇总

统一报告每次模型请求、每个用户轮次及每个业务任务的成本与耗时，并区分本地回答和含模型请求的回答。

> 每个成功任务的平均 API 成本 = 该批次全部任务的 API 成本 ÷ 成功任务数

分子包含失败任务、修正和额外调用的费用。没有成功任务时不计算；用量不明时说明统计不完整，不能记成免费。

单价表记录实际服务商、模型、计费项目、币种、核验日期和来源。正式测算时再核实价格，本方案不预填金额。估算费用与服务商实际账单分别标明。

### 3.4 服务依赖与恢复

建立服务依赖表，覆盖模型服务、代理端点（如使用）、托管平台、网络和本地资源。每项记录依赖用途、失败表现、现有控制、恢复方法及维护负责人。

## 4. 对 v1 开展正式评测

建议以 **12个开发任务 + 4个最终留出任务，每个重复3次** 为起点，并按预算调整。这是本项目的建议安排，不是教师指定数量。

覆盖以下任务类型：

- 正常查询与知识解释。
- 缺失、不可用记录和比较门槛。
- 日期、档案切换及多轮追问。
- 范围外请求、安全攻击和服务失败。

运行前固定数据快照，避免滚动日期改变标准答案。自动检查数字、参数和工具结果；人工检查用户最终看到的回答是否完整、有据。AI 可辅助评分，但需要用人工评分校准。

报告同时列出总体结果、各任务类型结果及重复一致性。未执行、中断、部分通过分别记录。48次任务尝试不等于48道独立题，也不等于48次模型请求；预算应按各任务的最大轮数和请求上限计算。

## 5. 建立商业测算表并开展对照

### 5.1 商业测算表结构

| 工作表 | 主要内容 |
| --- | --- |
| 参数与来源 | 使用量、人工单价、计费价格；标明实测、外部依据或假设 |
| 用户任务对照 | 看现有图表/说明与使用 SleepLens 的耗时、正确率、错误类型 |
| 运行成本 | API、托管、复核、内容维护、回归测试及一次性开发投入 |
| 商业情景 | 保守、基准、乐观情景下的成本、可货币化收益和盈亏条件 |
| 结论与证据 | 已证明什么、关键假设是什么、建议继续改进还是试点 |

### 5.2 小规模用户对照

先招募 **6–8位同学**，完成查数、两周比较、缺失解释和指标理解任务。比较以下两种流程：

- 对照流程：查看现有图表和字段说明，自行完成任务。
- SleepLens 流程：使用助手完成难度匹配的任务。

使用难度匹配的两套题，并交替安排使用顺序，减少记忆和练习影响。记录理解正确率、完成时间及错误类型。小样本结果作为探索性证据，多道题和重复操作不视为独立参与者。

### 5.3 区分用户价值和品牌收益

- **用户价值**：节省解读时间、提高理解正确率。
- **品牌价值**：可能减少客服工作、改善体验或带来付费收益，需要相应数据验证。

用户节省的时间，不能直接乘品牌员工工资作为现金收益。品牌测算公式为：

> 月净收益 = 可归因的客服成本节省 + 有证据支持的新增毛利 − API − 托管 − 复核 − 维护 − 预计错误处理成本

暂时没有证据的收益项保留为情景假设，开发投入单列。各情景明确使用量、采用率、任务成功率、人工介入及维护成本等假设，说明哪些变量会改变盈亏判断。

商业验收建议：用户对照达到预设目标，且基准情景有价值；保守情景下的亏损和剩余风险能够被明确解释和接受。

## 实施顺序与交付物

1. 完成第1、2步：确定指标、验收线、评分规则和版本记录结构。
2. 完成第3步：补齐任务关联、请求统计、实际耗时和成本计算能力。
3. 固定代码、配置和数据，冻结用于正式实测的 v1。
4. 开展第4、5步：真实模型评测、人工复核、用户对照和商业测算。
5. 形成对应的评价说明、逐题成绩、版本对比、运营汇总和商业测算表。

本方案只规划后续工作，不将拟定阈值、样本规模或情景金额当作已完成结果。
